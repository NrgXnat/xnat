Plugin authors/XNAT 1.11 /Jakarta · Tomcat 10

Porting your plugin to XNAT 1.11

1.11 moves XNAT to Jakarta EE and Tomcat 10.1. Your plugin needs at minimum a rebuild, and — if it touches Restlet, Turbine or Hibernate — source changes. Read the first three sections whichever way you work, then pick a track.

Read this first

A javax-compiled plugin doesn't "mostly work" on 1.11 — it takes the whole site down.

If your jar implements Spring's WebApplicationInitializer (most plugins with a REST API do, indirectly), XNAT throws AbstractMethodError during context startup, the entire web application fails to start, and every URL returns 404 — with no database error and nothing in the logs naming your plugin. Diagnosing that from the symptom alone is close to impossible unless you already suspect it.

Every plugin on a 1.11 site must be rebuilt for Jakarta. There is no mixed mode.

What 1.11 requires

Tomcat10.1
Java21
ActiveMQ broker6.x A 5.x broker fails to boot the Jakarta client silently — the app hangs rather than logging a clear error.

Before you start: get 1.11 on your machine

Changed 2026-09-10

1.11.0-SNAPSHOT is now published to the XNAT Artifactory. A build landed on 2026-09-10 (1.11.0-20260910.185426-1), so a plugin can resolve 1.11 from a remote repository. Building core yourself is no longer the only way in.

1.11 itself is still unreleased — what exists is a timestamped snapshot, and it moves when someone publishes again. Which of the two routes below you want depends on what you are doing, not on which is "proper".

Resolve it from the Artifactory

Nothing to build. Add the XNAT repositories to your plugin — most plugins already list them, in which case bumping vXnat to 1.11.0-SNAPSHOT is the whole change:

repositories {
    maven { url "https://nrgxnat.jfrog.io/nrgxnat/libs-release" }
    maven { url "https://nrgxnat.jfrog.io/nrgxnat/libs-snapshot" }
    mavenCentral()
}

Every coordinate a plugin build reaches for is published at that version:

  • org.nrg:parent — the BOM your dependencyManagement imports
  • org.nrg.xnat:web, org.nrg.xdat:core, org.nrg:framework
  • org.nrg:prefs, org.nrg:notify, org.nrg:config, org.nrg:automation
  • xnat-data-builder — the Gradle plugin your plugins {} block applies

To see which snapshot you are about to build against, ask the repository rather than guessing:

curl -s https://nrgxnat.jfrog.io/artifactory/libs-snapshot-local/org/nrg/parent/1.11.0-SNAPSHOT/maven-metadata.xml \
  | grep -E '<timestamp>|<buildNumber>'
The one trap on this route

A stale local publish silently wins. mavenLocal() is listed first in most plugin builds, so an older 1.11.0-SNAPSHOT sitting in ~/.m2 from a previous session shadows the Artifactory copy — and because the version string is identical, nothing tells you which one you got. If you are switching to this route, clear the old one:

rm -rf ~/.m2/repository/org/nrg

Or build core yourself

Still the right move in three cases: you are changing core alongside your plugin; you need a cutover commit newer than the published snapshot; or you want the Docker test stack, which lives in the same clone and is the subject of the next section. Clone the XNAT core repository next to your plugin and publish it locally:

git clone https://github.com/NrgXnat/xnat.git
cd xnat
git checkout feature/jakarta-cutover     # until 1.11 is merged and released
./gradlew publishToMavenLocal            # installs 1.11.0-SNAPSHOT into ~/.m2

One root invocation is enough — publishToMavenLocal runs in all 21 modules, and the satellite projects were merged into this repository, so there is nothing else to build first.

Confirm it worked before moving on

Two seconds here saves an hour debugging a resolution error that names the wrong thing:

ls ~/.m2/repository/org/nrg/parent/1.11.0-SNAPSHOT         # the BOM
ls ~/.m2/repository/org/nrg/xnat/build/xnat-data-builder   # the Gradle plugin
ls ~/.m2/repository/org/nrg/xnat/web/1.11.0-SNAPSHOT       # xnat-web

All three must exist. The middle one matters most and is the easiest to overlook: plugins apply xnat-data-builder in their plugins {} block, so if it's missing the build fails before any dependency resolution — with an error about the plugin rather than about XNAT.

Look wrong, aren't

xnat-data-builder publishes under a Gradle plugin-marker coordinate (org/nrg/xnat/build/…) rather than the usual artifact path, and dicom-edit6 carries its own version line — 6.9.0, not 1.11.0-SNAPSHOT. Neither indicates a failed publish.

The two reference documents

They live in that clone, which is why the agent prompt below points at a local path. If you took the Artifactory route and have no clone, read them on the branch instead — plugin-migration-guide.md and jakarta-plugin-port-handoff.md — and point your agent at the URL:

xnat/docs/ai/jakarta-plugin-port-handoff.md   # the procedure, for an agent
xnat/docs/plugin-migration-guide.md          # the reference catalog

And it is your test instance — you don't need a server from anyone

Finishing a port takes a running 1.11 instance: a plugin that compiles can still fail at load, and that failure stays invisible until you boot it. The same clone ships a Docker stack that boots the cutover WAR on Tomcat 10.1 / JDK 21, with PostgreSQL and ActiveMQ alongside. An agent with Docker access can stand this up itself.

./docker/stage-war.sh
echo 'file  /path/to/your-plugin/build/libs/your-plugin-…-xpl.jar' >> docker/plugins.manifest
./docker/stage-plugins.sh
docker compose up --build
docker compose logs -f xnat        # confirm your plugin is named as loaded
Skip the core build

stage-war.sh runs ./gradlew :xnat-web:war and copies the result to docker-context/xnat.war, which is the only thing the Dockerfile reads. If you took the Artifactory route, put the published WAR there yourself and skip the build — you still need the clone for docker-compose.yml and the scripts, but not for a 20-minute Gradle run:

curl -L -o docker-context/xnat.war \
  https://nrgxnat.jfrog.io/artifactory/libs-snapshot-local/org/nrg/xnat/web/xnat-web/1.11.0-SNAPSHOT/xnat-web-1.11.0-20260910.185426-1.war

That URL names one specific build. For whatever is newest, read maven-metadata.xml in the same directory and substitute the timestamp it reports.

Four things that bite people

Register the jar in docker/plugins.manifest — never hand-copy it into docker/plugins/. The staging script clears that directory first, so a copied jar silently disappears and you conclude the plugin "didn't load" when it was never staged.

Use the file entry form while iterating. The source form rebuilds from a repo checkout and refuses to run if that repo has uncommitted changes — the normal state of a port in progress.

XNAT scans the plugin directory once, at boot. After re-staging, docker compose restart xnat; re-running the staging script alone changes nothing in the running container.

A javax plugin fails here without naming itself. Every URL 404s and the webapp is dead. That's a successful reproduction of the bug, not a broken stack.

First boot runs schema creation and takes a few minutes — read the log rather than polling the port. For a genuinely clean slate, docker compose down -v before bringing it up again.

Choose a path

Track A

Port it with an AI coding agent →

You supervise. The agent does the mechanical work; you check its evidence. Fastest for a plugin with a large namespace sweep — and the sweep is usually ~80% of the diff.

Track B

Port it by hand →

Eleven steps, in the order that works. Each step surfaces the next set of errors; doing them out of order produces noise you'll chase for an hour.

Track A

Porting with an AI coding agent

The agent needs the procedure and the reference; without both it will improvise, and improvised ports look correct while being wrong in specific, known ways.

Step 1

Paste this, with the repository name filled in

Start the session in your plugin's clone, with the XNAT clone from the previous section nearby. Fill in the one path and paste:

Port this plugin (the repository in the current directory) to XNAT 1.11
(Jakarta / Tomcat 10).

The XNAT core clone is at <path-to-xnat-clone>. Before editing anything, read
both of these from it, and follow the handoff's phases in order:
  <path-to-xnat-clone>/docs/ai/jakarta-plugin-port-handoff.md   (procedure)
  <path-to-xnat-clone>/docs/plugin-migration-guide.md           (reference)

Build against vXnat = "1.11.0-SNAPSHOT". It is published to the XNAT
Artifactory (libs-snapshot, since 2026-09-10), so it should resolve from
there; I may also have a local publish in ~/.m2. If dependency resolution
cannot find org.nrg:parent:1.11.0-SNAPSHOT, check in order that the
libs-snapshot repository is declared, that a stale ~/.m2 copy is not shadowing
it, and that mavenLocal() is scoped to org.nrg.* -- then stop and tell me
rather than downgrading the version to something that does resolve.

Branch feature/tomcat10 off this plugin's develop, or main if it has no develop.

First, before any edit, report the framework surface so we both know the size of
the job: Restlet resources, Turbine modules, RunData overrides, and javax EE
references, each with the command you used.

Constraints:
  - Migrate javax -> jakarta BY PACKAGE, never by prefix. javax.annotation.Nonnull
    and Nullable (JSR-305), javax.cache, javax.xml.parsers, javax.sql and
    javax.naming do NOT move. Note that jsr250 javax.annotation.PostConstruct
    DOES move while jsr305 javax.annotation.Nonnull does not.
  - After converting Turbine overrides, run the Phase 3 verification grep from the
    handoff (the one that finds any doBuildTemplate / doPerform / isAuthorized
    still taking RunData) and paste its output. Do not simply assert the
    conversion is complete: a missed one still compiles and is silently never
    called, so the grep is the only evidence that counts.
  - Back every count, every "this is safe", and every bug-class definition with
    the command that proves it. If you cannot prove something, say it is
    unverified rather than asserting it.
  - A grep that returns nothing is a hypothesis, not a finding. If you expected
    matches and got none, widen the pattern before concluding.

Report these as three separate claims, not one:
  1. it compiles
  2. the tests pass
  3. the jar loads into a running 1.11 instance and it boots clean
Only (3) means done. Include the startup log line that shows the plugin loading,
and confirm no AbstractMethodError and no SEVERE.

For (3), stand the instance up yourself from the XNAT clone above — it ships a
Docker stack (stage-war.sh, plugins.manifest, stage-plugins.sh, docker compose
up --build); the handoff document has the exact sequence. If you have no Docker
access, say so and report (3) as unverified rather than implying it passed.

Finally: if you fixed a bug, sweep its class and state the class definition, the
audit scope and the result. And tell me explicitly what you did NOT do —
deferred items, unverified assumptions, anything you were unsure about.
Step 2

Check two things yourself when it reports back

These stay on your side of the line deliberately.

The prompt asks the agent to verify its own work, which helps — but the failure mode being guarded against is an agent that reports confidently without having checked. Asking it to promise it checked doesn't fix that. Two spot-checks cost a minute and don't depend on its cooperation:

  • Did the namespace sweep go too far? Search the diff for jakarta.annotation.Nonnull, jakarta.cache or jakarta.xml.parsers. Any hit means a blanket replace ran and broke things that never moved.
  • Is claim 3 actually claim 3? "Builds successfully" and "tests pass" get reported in language that sounds like done. If there's no startup log line quoted, the plugin was never loaded into a running instance.
Track B

Porting by hand — eleven steps

The order matters. Each step surfaces the next set of errors, and an unresolved dependency generates dozens of misleading cannot find symbol errors that vanish once resolution is fixed.

B1

Branch — after the prerequisite above

git checkout -b feature/tomcat10 develop   # or main, if there is no develop

Branch off your plugin's own mainline — not off an older migration branch.

B2

Size the job before editing

grep -rl 'import org.restlet' src/main/java | wc -l
find src -path '*turbine/modules*' -name '*.java' | wc -l
grep -rl 'RunData' src/main/java | wc -l
grep -rlE 'javax\.(persistence|servlet|validation|mail|jms|xml\.bind)' src/main/java | wc -l

All zero on the framework rows means this is a build-file-only port. Non-zero means source changes too.

B3

Update the build file

buildscript { ext { vXnat = "1.11.0-SNAPSHOT" } }
dependencyManagement.imports { mavenBom "org.nrg:parent:${vXnat}" }

repositories {
    // scope mavenLocal, or it shadows partial third-party artifacts
    mavenLocal { content { includeGroupByRegex 'org\\.nrg.*' } }
}

java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }
compileJava { options.fork = true }   // a cross-JDK toolchain must fork

// only if a screen calls data.getParameters()
compileOnly "org.apache.fulcrum:fulcrum-parser:4.0.0"
compileOnly "org.apache.fulcrum:fulcrum-pool:1.0.5"

Also rename the coordinates flagged in the matrix: turbine:turbine, velocity-engine-core, and the -jakarta Hibernate artifacts.

B4

Fix dependency resolution — and only that

./gradlew dependencies --configuration compileClasspath 2>&1 | grep -E "null|FAILED|Could not find"

Do not compile yet. A dependency that can't resolve produces "cannot find symbol" errors all over your source, and you will waste a cycle "fixing" code that was never broken. A common one: hibernate-core fails with an empty version rather than a helpful message, because the javax coordinate isn't managed by the 1.11 BOM.

B5

Sweep the namespace — by package, never by prefix

find src -name '*.java' -exec sed -i '' -E \
  's/javax\.(persistence|servlet|validation|mail|jms|transaction)/jakarta.\1/g' {} +

Never run a blanket javax→jakarta replacement. Note the trap: jsr250 javax.annotation.PostConstruct does move, while jsr305 javax.annotation.Nonnull does not — same package prefix, opposite answers.

grep -rhoE 'javax\.[a-zA-Z.]+' src/main/java | sort | uniq -c | sort -rn

What remains should be only JSR-305, JCache, JAXP, javax.sql and javax.naming.

B6

Remap Restlet imports, if you have Restlet resources

org.restlet.resource.Representation → org.restlet.representation.Representation, and the same for Variant. com.noelios.* is gone entirely. Replace dropped WebDAV status constants with local definitions.

B7

Convert Turbine overrides — then prove none were missed

// before
protected void doBuildTemplate(RunData data, Context context) throws Exception { … }

// after
protected void doBuildTemplate(PipelineData pipelineData, Context context) throws Exception {
    RunData data = pipelineData.getRunData();   // inserted; body unchanged
    …
}

Import org.apache.turbine.pipeline.PipelineData. Your own helper methods stay on RunData — only framework overrides change. Then:

grep -rnE '(protected|public)[^(]*(doBuildTemplate|doPerform|isAuthorized)[^(]*\([^)]*RunData' src/main/java

Any hit that is a framework override is a dead method: it compiles, and Turbine never calls it. This is the only change in the whole port that fails with no error at all, so verify it rather than trusting the edit.

B8

Compile, and expect two or three novel breaks

./gradlew compileJava

Match each error against the matrix and the guide's catalog. Expect a small number that aren't in either — that's normal; every plugin has some.

B9

Test-compile, then test-runtime

./gradlew compileTestJava
./gradlew test

compileOnly dependencies are absent from both, and each pass finds a different class of missing dependency.

B10

Build the plugin jar

./gradlew clean <pluginJarTask>    # e.g. xnatPluginJar, or fatJar

Use clean. If your plugin's version changed, a stale jar from the old version will sit alongside the new one and both may get deployed.

B11

Deploy to a real 1.11 instance and read the startup log

This step is not optional, and it is the one most often skipped.

If you don't have a 1.11 instance, make one — the XNAT clone from the prerequisite ships the Docker stack, and the commands are up there. Register the jar in docker/plugins.manifest, stage it, boot, and watch the log. You are looking for your plugin's "Found plugin" line, and for the absence of AbstractMethodError and SEVERE. A plugin that compiles perfectly can still fail the entire web context at load.

Traps worth knowing before you hit them

Fails silently

A missed RunData → PipelineData conversion compiles fine.

RunData extends PipelineData, so your old method is simply a more-specific overload Turbine never calls. The screen renders nothing, or the action never runs, and nothing is logged.

Compile-clean is not boot-clean

A plugin can build perfectly and still fail at runtime.

compileOnly dependencies are absent at deploy time, and unqualified bean injections that resolve inside your own tests can go ambiguous in the host context. Step B11 is what catches this.

Version changes leave stale jars

If your plugin's version string changes, the old jar doesn't disappear.

Both versions can end up deployed side by side, and XNAT will load both. Build with clean, and clear the target's plugin directory before copying.
